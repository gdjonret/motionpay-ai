# MotionPay AI audit — November 9, 2026

Historical findings before implementation. See [IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md) for the fixes, current verification, and remaining acceptance work.

MotionPay has a functioning sandbox prototype: conversational exercise help, three Wikimedia GIFs, video fallback, email authentication, a program recommendation, PayPal checkout, verified capture, and persistent account-linked access. The immediate priorities are reproducible judge access, recovery from failures, and an honest, coherent product experience. A redesign or another media-provider switch would have lower value before the deadline.

## Scope and evidence

Reviewed the Expo screens, shared catalog, media components, session lifecycle, API contracts, FastAPI endpoints, payment logic, SQL migrations, documentation, Git layout, asset credits, and submission requirements. No application behavior was changed during this audit.

Verification performed:

- 55 backend tests pass. Most external providers and payment storage are mocked.
- TypeScript and Expo lint pass.
- A fresh web production export succeeds at `/tmp/motionpay-audit-web`.
- Prior user-confirmed sandbox purchase/unlock is evidence of a successful real sandbox flow, not a substitute for independent repeatability testing.
- Reproduced the stale-exercise slowdown bug using the real chat handler without an LLM call.
- Reproduced expired pending-order failure with a mocked PayPal 404.
- Ran `npm audit --omit=dev`: five moderate entries, zero high/critical reported, in the Expo tooling dependency chain. Raw local results: `/tmp/motionpay-npm-audit.json`.
- Examined tracked files and remotes: only `mobile/` is a Git repository, no remote is configured there, source in `mobile/src/` is untracked, and the backend/migrations are outside that repository.

Not performed: a new purchase, a fresh phone walkthrough, screen-reader/device-size testing, independent database-policy execution tests, Python dependency vulnerability scanning, comprehensive secret-history scanning, load testing, or a penetration test. Successful compilation is not proof of runtime or security correctness.

## Fix before submission

### 1. P0 — The public submission repository is not prepared

Evidence: parent workspace has no Git repository. `mobile/` has an initial starter commit, no configured remote, and untracked source/assets. Its Git repository cannot include sibling `backend/` or `supabase/`. The only license is `mobile/LICENSE`, which contains Expo's starter copyright notice.

Impact: uploading only the existing mobile repository omits the backend and database migrations required to run MotionPay. A public repo cannot be verified from this local state.

Action: establish one repository containing mobile, backend, migrations, root instructions, environment examples, asset credits, and a top-level project license. Preserve required Expo and third-party notices. Review staged files and history for secrets before publishing. Do not blanket-license third-party media under the code license.

Acceptance: a clean clone contains all source, runs following the README, exposes no secrets, and has a detectable license and working public URL. Publicity must be verified remotely after publication.

### 2. P1 — Judge setup instructions are stale and fragmented

Evidence: `backend/README.md` says payments and authentication are not implemented; root README still says six exercises and describes older implementation state. The root run steps omit a complete coordinated account/database/payment setup.

Action: one authoritative setup path with Node/npm and Python 3.12 requirements, environment variable table, migration order, seller/buyer distinction, phone networking, exact startup commands, current eight-exercise coverage, and troubleshooting. Distinguish retrieved media from the actual squat speed transformation. Explain how judges obtain working test access without exposing server secrets in Git.

Acceptance: someone unfamiliar with the conversation can start the app and complete a sandbox purchase with documented access. Optionally host to reduce setup friction; hosting is not mandatory under the rules.

### 3. P1 — An expired pending order can block checkout indefinitely

Evidence: `backend/app/payments.py:90` fetches a stored pending order. A PayPal 404 raises an HTTP error caught as a generic 502, without clearing or reconciling that pending row. The unique pending-order index then preserves that same order as the next attempt.

Reproduction: mocked `access()` returns an expired pending ID and PayPal GET returns 404; `create_order()` returns 502 on each retry.

Action: distinguish terminal/expired orders from transient provider failure. Reconcile known terminal orders safely, preserve approved/completed orders for capture recovery, and offer a recoverable new checkout only when appropriate. Never treat a timeout as proof that payment failed.

Acceptance: expired checkout recovers; transient errors do not trigger another charge; an already completed capture can still unlock after a database/network interruption.

### 4. P1 before public hosting — AI and media endpoints lack abuse controls

Evidence: `backend/app/main.py:101`, `:199`, `:230`, and `:248` do not require identity or apply rate limits. Chat spends Groq quota; tutorial lookup spends YouTube quota. Browser CORS is not authentication and does not restrict direct HTTP callers.

Action: use authenticated access and per-user/IP limits, request/concurrency caps, caching for tutorial results, and bounded processing for slow-GIF requests. A deliberately public guest demo needs its own small allowance. Keep server keys private and the local development server off the public internet until controls are present.

Acceptance: repeated calls hit a predictable 429; paid-provider requests cannot be made without the intended access policy; normal demo requests still work.

### 5. P1 — Some copy advertises features that do not exist

Evidence: welcome and onboarding advertise personalized workout plans and personalized coaching; the app recommends one static template. Progress is a `TabPlaceholder`. Onboarding's format selector changes captions but the same image remains displayed.

Action: describe the implemented experience: conversational exercise explanations, stored demonstrations, and an optional training template. Hide or clearly label unfinished progress tracking. Keep the claim that the squat playback can be slowed, but do not describe GIFs as newly generated exercise motions.

Acceptance: every claim in onboarding, submission description, and video can be demonstrated on the actual build.

### 6. P1 — The program does not yet justify its presentation

Evidence: `backend/app/payments.py:151` duplicates identical sessions across all four weeks. The paid-content UI prints exercise names as strings without opening their demonstrations, while the offer includes demonstrations and instructions.

Action: give each week a meaningful focus or supported progression, describe what remains a prototype, and connect each program exercise to its existing detail/demo screen using stable IDs. Add rest/warm-up guidance and explain equipment, without claiming professional review or individualized suitability. Do not invent complexity just to differentiate weeks.

Acceptance: users can open an exercise demonstration directly from their unlocked session and understand the purpose of each week.

### 7. P1 — “Make it slower” can select the wrong exercise

Evidence: `backend/app/main.py:104` chooses the most recent non-null assistant exercise ID. A later YouTube-only exercise has no ID, so the earlier catalog selection remains eligible.

Reproduction: show squat → show kettlebell-swing tutorial → make it slower. Handler selects `bodyweight-squat`.

Action: maintain an explicit current demonstration identity including external-media queries, clear/replace it when the displayed exercise changes, and explain unsupported speed control for the current media. Expand supported phrasing only after correctness is reliable.

Acceptance: follow-ups apply to the most recent demonstration; no older movement silently reappears.

### 8. P1 — Chat is not scoped to the signed-in account

Evidence: `mobile/src/app/(tabs)/coach.tsx` keeps messages and history in component state/refs without an auth-user key or sign-out reset. Profile sign-out leaves the tabs mounted.

Impact: when the same running app changes users, previous messages may remain visible and enter subsequent AI history. This is a local-session privacy issue, not evidence of a cross-account database leak.

Action: clear chat on account change/sign-out or isolate it by user. Persist only if explicitly implemented with appropriate account permissions. Reset the hard-coded “GD” avatar too.

Acceptance: user B never sees or submits user A's prior conversation, including while an earlier request is in flight.

## Improve the core experience next

### 9. P2 — Chat becomes awkward and expensive as it grows

Evidence: all messages/media mount inside one `ScrollView`; the composer and suggestions live inside that same scroll content; there is no automatic scroll-to-reply, history persistence, or new-chat action. Only the latest 12 turns are sent to the model while older messages remain visible.

Action: keep the composer anchored above the keyboard, move suggestions into the empty state, scroll to new replies without interrupting manual reading, virtualize long lists, pause offscreen media, and provide New chat. Show clear loading and retry states. Explain or manage context truncation.

Acceptance: after 20 exchanges on a small phone, the input remains accessible, the newest response is easy to find, and media does not all animate in the background.

### 10. P2 — Recommendation ownership checks can mislead during errors

Evidence: `ProgramRecommendation.tsx:22` swallows lookup failure and marks the check finished while `owned` remains false. `program.tsx:60` enables checkout while ownership is still unknown. Backend rejects an owned purchase, so these are misleading UI states rather than a demonstrated duplicate-charge path.

Action: explicit loading/error/owned/unowned states; on failure show “Check access” or “View details,” not a confirmed purchase offer. Share one access cache rather than fetching once per recommendation card. Do not lose the program destination after sign-in.

Acceptance: a network error never labels an existing purchase as unowned; signing in from the program returns to it.

### 11. P2 — Manual checkout return adds friction

Evidence: PayPal opens through `Linking.openURL`; browser return pages instruct a manual app switch and Verify payment. The return page says “Approval received” without independently checking order state, although it correctly grants no access.

Action: keep the explicit verify path as a reliable fallback. Add safe return/deep-link handling appropriate to Expo Go versus a development build; reconcile when the app becomes active, still verifying server-side. Make return-page wording neutral until status is checked. Handle expired session during verification.

Acceptance: switching back after approval presents a clear verification state; browser visits or fabricated return URLs cannot unlock anything.

### 12. P2 — Price and product metadata are duplicated

Evidence: mobile `programs.ts` holds $9.99, the system prompt repeats it, and order creation reads the database. Server charging is authoritative, but a future database price change could make the displayed price or AI response wrong.

Action: expose one server-owned program summary and use it in product cards, checkout review, and AI context. Persist the price/version agreed at order creation. Prefer integer/Decimal formatting for money.

Acceptance: changing the configured program price cannot produce a different UI price from the approval amount.

### 13. P2 — Exercise retrieval still depends heavily on prompt compliance

Evidence: schema validates catalog IDs but selection relevance, medical exclusions, and program relevance are mostly prompt instructions. Jumping jacks has a special deterministic repair; other requests do not. Client-supplied history also carries unverified `exercise_id` text into the model.

Action: add a small evaluation set for greetings, exercise synonyms, ambiguous requests, equipment constraints, declined purchases, injuries, and multi-turn follow-ups. Resolve exact aliases deterministically where safe; require clarification for genuinely ambiguous requests. Validate history metadata and keep purchase actions outside model control. Render markdown intentionally or constrain text to plain text.

Acceptance: demonstrated success across a representative set, not only one successful prompt. Unit tests with mocked model output verify plumbing, not real model judgment.

### 14. P2 — Media selection and playback need curation

Evidence: YouTube search chooses the first structurally valid video ID without validating exercise equivalence or instructional quality. Several non-GIF exercises render both a video fallback and illustration sequence. A disabled WorkoutX request adds an extra network round-trip before YouTube. GIFs lack pause/reduced-motion controls.

Action: pin reviewed tutorial IDs for the small demo catalog, choose one primary visual with an alternate option, skip disabled providers, and provide pause/reduced-motion behavior. Cache bounded lookup results. Preserve source/author/license links and review the artwork and form manually.

Acceptance: the demo catalog shows the intended exercise on the first attempt, remains readable, and degrades to an explicit alternate link on playback failure.

### 15. P2 — Account recovery and session storage remain prototype-level

Evidence: sign-up, sign-in, and sign-out are implemented; recovery/resend flows are absent. Native sessions use AsyncStorage. No privacy/data-handling explanation is provided, although conversations are sent to Groq and user metadata is stored in Supabase.

Action: document the actual data flow, add recovery/resend with tested redirects, and evaluate platform-secure token storage for a shipped app. Show a setup/error state for unavailable auth. Review the sign-in form's pending/disabled and accessibility behavior.

Acceptance: a judge can recover or use a documented test account, and users understand where their data goes.

## Payment hardening after the immediate recovery fix

### 16. P2 — Order creation is not durably idempotent across interrupted attempts

Evidence: capture reuses `capture-{order_id}`, which is good. Creation generates a new UUID for every attempt and saves the local purchase after the PayPal call. A timeout after remote creation or a failed insert can leave an orphan PayPal order. The pending unique index prevents multiple stored pending orders, but is not an atomic reservation spanning PayPal and Supabase.

Action: persist a checkout attempt/idempotency key before the provider call, reserve concurrent attempts, and reconcile remote results. Keep current capture recovery and atomic completion. Test concurrent create/capture and storage failure after capture. Verify expected association and order amount before initiating capture as an additional safeguard, not just before unlock.

Acceptance: retrying the same attempt reuses the same remote order; concurrent requests have a defined result; a completed charge is never followed by instructions to pay again.

Reference: https://developer.paypal.com/api/rest/reference/idempotency/

### 17. P2/later — Production payment lifecycle is intentionally incomplete

Evidence: sandbox-only URLs, no webhook reconciliation, refund/reversal handling, purchase-history screen, or access revocation flow. A capture ID is checked structurally but provider completion responses are not persisted as audit events.

Action: keep this explicitly sandbox-only for submission. Before real commerce, implement authenticated webhook verification, reconciliation, refunds/revocation policy, audit records, operational alerts, and trusted price/content administration. The AI should recommend and explain; it must never authorize purchases.

Acceptance for hackathon: sandbox label everywhere, one purchase, cancellation, retry, and account isolation all demonstrated. Production readiness is a separate milestone.

## Engineering and release work

### 18. P2 — Tests do not cover several key integration boundaries

Evidence: passing suite covers rejection cases and completed-order retry; the normal approved-order POST capture, create-order contract, actual SQL policy/RPC transaction, and mobile ownership state transitions are not fully covered. No CI workflow is present in the reviewed project.

Action: prioritize meaningful tests for those boundaries, expired-order recovery, account switching, cancelled checkout, and content access denial. Add CI for backend tests plus lint/typecheck/build. Run migrations against a clean test Supabase instance. Avoid adding tests that only mirror UI styling.

Acceptance: a clean database and clean clone can reproduce the full flow, and CI catches a broken provider contract.

### 19. P2 — Dependencies and observability need a deliberate maintenance path

The npm scan reports five moderate entries involving `expo`, `@expo/cli`, `@expo/fingerprint`, `glob`, and `minimatch`; some are propagated dependency findings. They are not five proven remotely exploitable mobile bugs. The specific underlying advisories include glob cancellation traversal and minimatch denial of service. npm proposes an incompatible Expo 52 downgrade as its automatic fix, so do not run `npm audit fix --force` blindly.

Action: review compatible Expo patch releases and dependency overrides with testing, avoid exposing Metro publicly, and scan Python dependencies separately. Add sanitized structured request/error logs and readiness checks for database/payment configuration. Cache PayPal OAuth tokens until near expiry to reduce latency, without logging them.

Acceptance: documented dependency decisions, compatible builds, and actionable logs without tokens or secrets.

Advisories: https://github.com/advisories/GHSA-3g3m-2fjr-6pw4 and https://github.com/advisories/GHSA-g3hv-75wg-m249

### 20. P2 — Submission assets and runtime availability are unfinished

Evidence: no final project description/demo script/public repository URL/deployment configuration was found in the workspace. Existing READMEs and credits are a starting point, not a complete submission. Media credits cover the GIFs, but all welcome art and any recorded third-party material should also be accounted for.

Action: prepare a public repository and clear run instructions OR hosted demo, tool/model explanation, under-three-minute public YouTube video showing the actual device, and working judge access through the judging period. Record the approved sandbox buyer flow, not the seller login confusion. Show a specific audience: beginners who want a quick movement demonstration and a structured next step.

Reference: https://paypalaihackathon.devpost.com/ (deadline November 12, 2026, noon PST). Rules: https://paypalaihackathon.devpost.com/rules (judging access through December 15).

## Recommended sequence with the time remaining

1. Stabilize checkout recovery, account-scoped chat, slowdown context, and public API access limits. Keep automated regression tests for these failures.
2. Align copy, hide unfinished features, make the program useful and its demos directly accessible. Do not add another exercise provider.
3. Establish the complete public repository/license, replace stale docs, and run a clean setup rehearsal.
4. Test one fresh account end-to-end on phone: greeting → GIF → follow-up → relevant recommendation → review → cancel → resume → approve → verify → open → restart → still owned. Check a second account stays locked.
5. Record the concise device demo and submit November 11 if possible, leaving November 12 as buffer.

Do not spend the remaining days on a large catalog, custom video generation, social features, analytics dashboards, a native 3D renderer, or production-payment scope. The working narrow product is the asset to polish.
